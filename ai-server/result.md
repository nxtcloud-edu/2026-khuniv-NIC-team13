## 측정 조건

- 입력 파일: `python/scripts/sample_analyze_request.json`
- 입력 SHA-256: `9331fa84d688cfa4af30fe913509d5390d7874ee6b9ec862ade913dc09d7eaa7`
- 검증된 입력 규모: 질문 3개, 답변 3개, 질문 125자, 답변 735자
- 실행 명령:

  ```bash
  cd python
  ../.venv/bin/python scripts/benchmark_sample_pipeline_20runs.py \
    --request scripts/sample_analyze_request.json --runs 20
  ```

- 측정 스크립트: `python/scripts/benchmark_sample_pipeline_20runs.py`
- 실제 설정된 EXAONE/Friendli, OpenAI embedding, Tavily, DynamoDB, S3 Vectors 및 LangSmith 경로를 사용하는 `Container`로 실행했다. fake/mock 값은 사용하지 않았다.
- 프로세스 시작과 `Container` 생성은 1회만 했고, 같은 입력으로 워크플로를 20회 순차 실행했다. 따라서 서비스의 장기 실행 상태와 같이 2회차부터 WebSearch 캐시가 재사용됐다.
- 각 노드의 실제 `execute()` 호출 전후를 `time.perf_counter()`로 감쌌다. 노드 재시도가 있으면 해당 노드 시간은 모든 시도의 합이다.
- 전체 응답 시간에는 워크플로 제어 및 tracing 시간이 포함된다. 프로세스 시작·의존성 import·`Container` 생성 시간은 포함하지 않는다.
- 점수, fallback, 실패, 출력 fingerprint와 유사도는 실행 중 생성된 상태와 이벤트에서 수집했다. 임의 값을 채우지 않았다.

## fallback 구간과 횟수

| 이벤트 | 노드/구간 | 횟수 | 발생 회차 | 의미 |
|---|---|---:|---|---|
| `pass_score_none` | DATA | 20 | 1~20 | 이전 평가 평균을 얻지 못해 대체 경로 사용 |
| `workflow_retrying` | 엔진 → EVALUATE | 2 | 2, 17 | EVALUATE 예외 후 노드 재시도 |
| `evaluate_strategy_fallback` | EVALUATE strategy | 2 | 3, 4 | 모델의 strategy 출력을 사용하지 못해 로컬 strategy 사용 |
| `revise_targeted_repair` | REVISE, 문항 2 | 17 | 3~13, 15~20 | 첫 수정 답변이 검증을 통과하지 못해 문항 2만 재생성 |
| `revise_safe_fallback` | REVISE, 문항 2 | 15 | 5~13, 15~20 | 재생성도 검증 실패해 원래 답변을 안전하게 보존 |

- 모든 회차가 `pass_score_none`을 포함하므로 넓은 의미의 fallback 없는 회차는 0/20이다.
- DATA의 공통 대체 경로를 제외하고 모델 출력 관련 복구가 전혀 없었던 회차는 1, 14회차의 2/20 (10%)뿐이다.
- REVISE에 도달한 19회 중 문항 2의 첫 생성 검증 통과는 2/19 (10.53%)뿐이다. 전체 20회 기준 17/20에서 국소 재생성을 했고, 15/20에서는 재생성도 실패해 원문 보존으로 끝났다.
- REVISE에서 반복 검출된 구체적 문제는 원문에 없는 숫자 `12` 추가와 태국 문자 혼입이었다. validator가 이를 차단했기 때문에 파이프라인은 성공했지만, 성공률만 보면 모델 원출력의 낮은 안정성이 가려진다.
- 벤치마크 로그에서는 S3 Vector 조회가 자격 증명을 찾지 못해 20/20 비차단 fallback으로 끝났다. 임베딩 호출은 그 전에 수행되므로 외부 embedding 비용과 시간은 쓰고도 벡터 문맥은 사용하지 못한 상태다.

## 진단과 권장 수정

1. **EVALUATE 출력 길이 제한을 가장 먼저 해결해야 한다.** 최종 실패 1회와 복구된 지연 1회의 직접 원인이 모두 completion 4,096 tokens 도달이었다. 각 Evaluate 하위 호출의 `max_tokens`를 실제 스키마별로 더 작게 제한하고, 장문 자유서술 필드의 최대 길이를 prompt와 validator 양쪽에 둬야 한다. 같은 요청을 통째로 재시도하면 30~70초와 토큰을 추가로 소비한다.
2. **level을 모델에게 맡기지 말고 x/y/z에서 코드로 계산해야 한다.** 19회 점수가 완전히 같은데 level이 한 번 달랐다. 임계값을 명시해 결정적으로 산출하면 이 불일치를 제거할 수 있다.
3. **REVISE의 문항 2 복구 경로를 재설계해야 한다.** 85%가 targeted repair, 75%가 safe fallback이었다. 질문 echo·금지 문자·지원되지 않는 숫자처럼 기계적으로 판별 가능한 것은 생성 후 결정적 정리로 먼저 처리하고, 의미가 바뀌는 경우에만 한 번 재생성하는 편이 토큰과 지연을 줄인다.
4. **safe fallback 사용을 성공과 분리해 품질 지표로 노출해야 한다.** 현재는 원문 보존이어도 워크플로 성공이다. API 결과 또는 관측 지표에 `revised=false`/`fallback_reason`을 남겨 실제 개선 성공률을 볼 수 있어야 한다.
5. **DATA/S3 자격 증명 전달 경로를 명시적으로 확인해야 한다.** 직접 실행에서는 S3 Vector가 `NoCredentialsError`로 20회 모두 실패했다. 현재 boto3 client는 애플리케이션 Settings의 키를 전달하지 않고 기본 credential chain을 사용한다. 운영도 같은 실행 방식이면 `.env`를 Settings가 읽는 것만으로는 boto3 자격 증명이 되지 않을 수 있다. 비밀 값 자체를 기록하지 말고 시작 시 credential provider 사용 가능 여부와 비차단 fallback 카운터만 남기는 것이 안전하다.
6. **`pass_score_none`의 원인을 관측 가능하게 분리해야 한다.** 현재 repository scan은 예외를 `None`과 동일하게 취급하므로 “실제 비교 데이터 없음”과 “AWS 접근 실패”를 결과만으로 구분할 수 없다. `no_match`, `credential_error`, `timeout`, `service_error`를 별도 이벤트/metric으로 기록해야 한다.
7. **캐시 cold/warm 성능을 분리해서 봐야 한다.** 이번 20회는 실제 장기 실행 서비스처럼 첫 회만 Tavily를 호출했다. 독립 cold request 성능을 알고 싶다면 매회 새 Container 또는 WebSearch cache 초기화 조건으로 별도 측정해야 한다. 현재 결과에서 첫 회 37.993초와 warm 정상 구간 23~31초를 같은 평균 하나로만 보면 원인이 흐려진다.
8. **LangSmith 종료 처리의 중복 update를 확인해야 한다.** 2회차 최종 실패 때 동일 span에 대한 409 duplicate update가 관찰됐다. 실패 patch 후 공통 종료 경로가 같은 run을 다시 갱신하는지 확인하고, trace 종료를 한 위치에서 한 번만 수행해야 한다.

## 결론

제공된 동일 sample 파일 기준 최종 성공률은 95%, 점수 일관성은 100%였다. 다만 이 수치만으로 안정적이라고 보기는 어렵다. EVALUATE 길이 제한이 10%의 회차에서 발생했고 5%는 최종 중단됐으며, REVISE는 85%가 국소 재생성에 들어가고 75%가 원문 보존 fallback으로 끝났다. 현재 파이프라인은 **낮은 모델 출력 안정성을 validator와 fallback으로 안전하게 흡수하지만, 그 대가로 지연·토큰·실제 개선률 저하가 발생하는 상태**다.
